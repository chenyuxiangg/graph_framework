## 3.1 执行拓扑（所有权模型）

**核心决策：RunState 由且仅由一个"run 事件循环任务"独占；执行任务只持不可变快照 + 回传通道。**

```text
                ┌──────────────────────────────┐
   控制通道 ───▶ │   Run Event Loop (per run)   │ ◀── 执行结果通道（mpsc）
  (高优先 mpsc)  │   独占 RunState               │
                │   不执行任何同步 Python        │
                └──────────────┬───────────────┘
                               │ 派发（spawn）
                ┌──────────────▼───────────────┐
                │  Executor Task (per instance) │
                │  ├─ PythonHandler → worker 子进程（M3；M2 FakeExecutor）
                │  ├─ AgentHandler  → Harness（async；tool 经 worker 子进程）
                │  └─ Start/End     → 直接返回
                │  完成后：评估出边内置 gate op（off-loop）→ 发回 NodeCompleted
                └──────────────┬───────────────┘
                               │ 不可丢 trace 事件
                ┌──────────────▼───────────────┐
                │  Trace Writer（独立 std 线程） │ → SQLite（批量事务）
                └──────────────────────────────┘
```

| 组件 | 线程/任务 | 职责 | 禁止 |
|---|---|---|---|
| Run Event Loop | 每 run 一个 tokio task，独占 `RunState` | 消费事件、迁移状态、应用投递、就绪派发、终止判定 | 同步 Python、同步 SQLite、阻塞 IO |
| Executor | 每实例一个 task | 调 handler；**off-loop 评估出边 gate**；回传结果 | 改 `RunState`、发 trace 以外的共享写 |
| Python Worker | M3：每节点一个 worker 子进程（独立进程组），supervisor 异步等待 | 执行 Python 节点/工具；超时/取消 = kill 进程组 | 在事件循环线程内同步 wait / 阻塞 |
| M2 等价物 | in-process `FakeExecutor`（同进程 tokio task） | M2 垂直切片；"kill" = `abort()` | 同左（禁止在事件循环内直调用户 Python） |
| Trace Writer | 独立 OS 线程（`blocking_recv`） | 批量写 SQLite | 反向调用内核 |
| Control Channel | 独立 mpsc（unbounded） | Pause/Resume/Cancel | 与数据事件混排（审计 C-13） |
| Watchdog | 每 run 一个 interval task → `Tick` 事件 | 超时扫描、静默检测、记账 | 直接改状态（必须走事件） |

> **与 v1.1 的差异**：v1.1 说"Scheduler 是单线程事件循环"，实际落地为**每个 run 一个事件循环任务**（多 run 并发），单 run 内部严格串行。多线程 runtime 不破坏 I1/I2，因为状态不跨任务共享。
>
> **M2/M3 执行口径（D1/D4）**：M2 垂直切片用 **in-process `FakeExecutor`**——执行任务是同进程 tokio task，"kill" = `abort()`（等价语义：停止等待、实例 TimedOut、`killed_workers += 1`）。M3 起每个 Python/Agent 节点一个 **worker 子进程**：事件循环只**异步等待** supervisor，超时/取消 = **杀进程组**（见 §3.9）。表内 "Python Worker" 行即 M3 的形态；M2 无真实 OS 进程。

## 3.2 启动流程（关闭审计 S-01）

```rust
pub struct RunSpec {
    pub graph: Arc<CompiledGraph>,
    pub entry_inputs: HashMap<NodeId, HashMap<PortName, Value>>, // 必须覆盖 entry 节点的 required
    pub user_id: String,
    pub global_vars: HashMap<String, Value>,
    pub options: RunOptions,
}

pub struct RunOptions {
    pub deadlock_grace_ms: u64,        // 默认 DEADLOCK_GRACE_MS
    pub python_concurrency_cpu: usize, // 默认 PYTHON_CONCURRENCY_CPU
    pub python_concurrency_io: usize,  // 默认 PYTHON_CONCURRENCY_IO
    pub trace_enabled: bool,           // false 时不写 SQLite（仅测试/CLI --no-trace）
    /// 仅测试构建可用（`#[cfg(any(test, feature = "test-hooks"))]`）：故障注入入口。
    /// 用于 AC-11「禁用 settle 制造死锁」等场景；生产二进制中该字段不存在。
    pub test_hooks: TestHooks,
}

pub struct TestHooks {
    pub disable_settle: bool,          // 不结算入边 → 触发死锁检测
    pub force_node_timeout_ms: Option<u64>,
    pub fail_trace_write_after: Option<u64>, // 模拟磁盘满（AC-06/存储 fail-stop 测试）
}
```

启动步骤（**原子完成，期间不接受控制命令**）：

| # | 动作 | 失败时 |
|---|---|---|
| 1 | 校验 entry_points 非空、每个 entry 在节点表、`entry_inputs` 无多余节点/端口 | `RUN_ENTRY_INVALID` → 启动失败（不产生 run） |
| 2 | 校验每个 entry 节点的 required 端口都被 `entry_inputs` 覆盖 | `RUN_ENTRY_INPUT_MISSING` → 启动失败 |
| 3 | 创建 `RunState`（status=Running，生成 `run_id`） | — |
| 4 | 按 `node_order` 顺序，为每个 entry 创建实例（`Pending`、`attempt=0`），写 buffer（全部 entry_inputs），结算"外部注入" | — |
| 5 | 对每个 entry 实例做就绪判定（通常恒真）→ `Ready`；入 `ready_queue` | — |
| 6 | 发 `RunStarted{run_id, graph_hash, user_id, at}`（不可丢，`send().await`） | trace 写失败 → run Failed（fail-stop） |
| 7 | 进入事件循环 | — |

**多入口**：全部入口实例在步骤 4 一次性创建，按 `node_order` 顺序入队（确定性）。

## 3.3 主循环

```rust
async fn run_loop(mut run: RunState, mut exec_rx: mpsc::Receiver<RuntimeEvent>,
                  mut ctrl_rx: mpsc::Receiver<RunControl>, mut tick: Interval) {
    loop {
        // 1) 控制命令优先（biased select；审计 C-13）
        if let Ok(cmd) = ctrl_rx.try_recv() { handle_control(&mut run, cmd); }

        tokio::select! {
            biased;
            Some(cmd) = ctrl_rx.recv() => { handle_control(&mut run, cmd); }
            _ = tick.tick() => { watchdog(&mut run); }
            Some(ev) = exec_rx.recv() => { handle_exec_event(&mut run, ev).await; }
            else => break,
        }

        // 2) 统一应用阶段：投递 → 结算 → 就绪 → 派发 → 终止判定
        drain_pending_deliveries(&mut run).await;   // 见 3.4
        dispatch_ready(&mut run).await;             // 见 3.5
        if is_quiescent(&run) { finish_run(&mut run, RunEnd::Completed).await; break; }
        if run.status.is_terminal() { break; }
    }
}
```

**顺序保证**：同一批次内先应用投递再派发；派发按 `ready_queue` FIFO；`ready_queue` 入队顺序 = 事件到达顺序 + 边顺序（确定性，可回放）。

## 3.4 投递应用（关闭审计 C-23/双写、P-04）

`publish` 拆成两段：**求值（off-loop，在执行任务内）** + **应用（on-loop，事件循环内）**。

### 3.4.1 求值（执行任务内，off-loop）

执行任务在 handler 返回后，对每条出边计算 gate：

```rust
// 在 executor task 内（gate = 内置 op，Rust 实现；不进事件循环线程）
let mut evaluations = Vec::new();
for edge_idx in graph.edge_index.outgoing[&node_id] {
    let edge = &graph.edges[edge_idx];
    let passed = match &edge.gate {
        None => true,
        Some(g) => evaluate_gate(g, &output, &gate_ctx),  // 严格 bool；异常 = false + error 记录
    };
    evaluations.push(GateEvaluation { edge_index: edge_idx, passed, error });
}
tx.send(RuntimeEvent::NodeCompleted { run_id, instance_id, output, evaluations });
```

> **为什么 gate 不在事件循环里求值**：v2 的 gate 是内置 op（D6，Rust 实现），但求值仍放在执行任务内 off-loop，保证事件循环只做确定性投递应用；历史上同步 Python gate 实测可阻塞事件循环 405–1500ms，该约束继续成立。

### 3.4.2 应用（事件循环内，同步、确定性）

```rust
async fn apply_completed(run: &mut RunState, instance_id, output, evaluations) {
    // 1) 状态迁移 Running → Completed（若实例已终态则丢弃迟到结果）
    if !transition(run, instance_id, Completed, "execution ok").is_ok() { return; }
    run.instances[&instance_id].output = Some(output.clone());

    // 2) 逐边生成并应用（按 EdgeIdx 升序）
    for eval in evaluations.sorted_by_key(|e| e.edge_index) {
        let edge = &run.graph.edges[eval.edge_index];
        let target = resolve_target_instance(run, instance_id, edge); // 自环→新建；否则 get_or_create
        let record = GateResultRecord { ..., passed: eval.passed, error: eval.error };
        run.trace_tx.send(TraceEvent::GateResult { record }).await;   // 不可丢

        if eval.passed {
            buffer_write(run, target, &edge.to_port, output.clone());
            settle_edge(run, edge.to_node, edge.index);
            maybe_make_ready(run, target);          // 1.3 就绪判定
        } else {
            settle_edge(run, edge.to_node, edge.index);
            maybe_skip(run, edge.to_node);          // 见 3.6 Skipped 级联
        }
    }
}
```

**Skipped 级联算法（关闭审计 C-07/S-10）**：

```text
maybe_skip(run, node):
  if node 已有实例且状态 != Pending: return
  all_in = edge_index.incoming_by_node[node]
  if settled_by_node[node] ⊇ all_in:          // 所有入边都已结算
     if buffer 有数据且 ready():  → Ready（保留）
     else                       → Skipped（reason="all_sources_blocked"）
        for out_edge in outgoing[node]: settle_edge(run, out_edge.to_node, out_edge.index)
        for each target: maybe_skip(run, target)    // 递归级联（迭代实现，避免深递归）
```

> 注意 `settled_by_node` 是**节点级**集合：只有当所有入边都结算且无可用数据时才是 Skipped。

## 3.5 就绪与派发

```rust
async fn dispatch_ready(run: &mut RunState) {
    while let Some(inst) = run.ready_queue.pop_front() {
        if run.instances[&inst].status != Ready { continue; }       // 取消/失败后跳过
        if run.status != Running { run.ready_queue.push_front(inst); break; } // Paused
        transition(run, inst, Running, "dispatch").await;
        let inputs = build_inputs_snapshot(run, inst);              // 深拷贝；Any 未到端口填 null
        let ctx = NodeContext::new(run, inst);                      // 只读视图
        let (tx, slot) = (run.exec_tx.clone(), run.worker_slot());  // 全局/每 run worker 名额（D4）
        let node = &run.graph.nodes[&run.instances[&inst].node_id];
        let deadline = Instant::now() + Duration::from_millis(node.timeout_ms);
        run.deadlines.insert(inst.clone(), deadline);   // 01 §1.6；事件循环侧统一判定
        tokio::spawn(exec_instance(inst, handler, inputs, ctx, tx, slot, deadline));
        // 超时由事件循环侧记录 deadline（见 3.9）
    }
}
```

**派发约束**：
- **全部声明端口都出现在 inputs 中**：`trigger=Any` 的未到 required 端口填 `null`；optional 未到端口也填 `null`（Python 侧统一 `None`，04 §4.3 / 00 §0.7）。
- 每次派发前 `debug_assert!(ready(...))`（I3 双检）。
- 同一实例只派发一次（I1：状态迁移 Running 后不会回到 Ready）。
- **worker 并发上限（D4）**：全局 `MAX_WORKERS = CPU 核数 × 2` + 每 run `MAX_WORKERS_PER_RUN = 8`（00 §0.5）；派发前先取全局名额再取 run 名额，取不到则暂缓派发（实例保持 Ready）。**每节点一进程**，不再使用 CPU=1 / IO=4 解释器信号量；`config.exec_class` 保留但**忽略**（池化时再启用）。

## 3.6 完成/失败/超时的统一入口

| 事件 | 处理 |
|---|---|
| `NodeCompleted` | `apply_completed`（3.4.2） |
| `NodeFailed` | `transition(Crashed)` → `fail_run(RunEnd::Failed{error})`（冷峻） |
| `NodeTimedOut` | `transition(TimedOut)` → `fail_run(RunEnd::Failed{error: Timeout})` |
| `NodeCancelled` | `transition(Cancelled)`；若因 run 取消则继续收尾 |
| `Tick` | watchdog：超时扫描、静默检测、记账 |

**迟到结果**：实例已终态时，`NodeCompleted/Failed` 直接丢弃并记 warning（关闭审计 S-09）；不改变 run 状态。

## 3.7 冷峻失败传播（关闭审计 C-09/C-10/I9）

```rust
async fn fail_run(run: &mut RunState, end: RunEnd) {
    if run.status.is_terminal() { return; }
    run.cancel.store(true, Ordering::SeqCst);
    run.status = RunStatus::Failed;

    // 1) 所有非终态实例 → Cancelled（Running 同时置协作取消标志）
    for inst in run.instances.values_mut() {
        if !inst.status.is_terminal() {
            let from = inst.status;
            inst.status = Cancelled;
            inst.finished_at = Some(now());
            emit_transition(from, Cancelled, "run failed");
        }
    }
    // 2) 丢弃 ready_queue / 未应用投递
    run.ready_queue.clear();

    // 3) flush 不可丢 trace + RunFinished（恰好一次，I5）
    trace_flush(run).await;
    run.trace_tx.send(TraceEvent::RunFinished {
        run_id: run.run_id.clone(), status: RunStatus::Failed,
        error: Some(end.error()), at: now(),
    }).await;
    run.finished_at = Some(now()); run.status = RunStatus::Failed;
}
```

**要点**：
- 失败**终止**在飞任务（D1：M2 = `abort()` 任务；M3 = kill worker 进程组，见 §3.9），不等其自然结束；被杀 worker 计入 `RunMetrics.killed_workers`（`abandoned_tasks` 恒 0）。
- 已 `Completed` 的实例不改（保留其 trace）。
- 失败后到达的任何事件一律丢弃。
- `RUN_ILLEGAL_TRANSITION` / `RUN_DELIVERY_TO_TERMINAL` / `RUN_PYTHON_INIT` / 任务 panic 全部进入 `fail_run`（不同 error）。

## 3.8 控制语义（关闭审计 C-11/C-13/C-14、S-05）

控制命令走**独立 unbounded mpsc**，`select! biased` 中优先于执行事件（C-13 修复）。

| 命令 | 前置状态 | 行为 | 后置 |
|---|---|---|---|
| `Pause` | Running | 停止派发（`ready_queue` 冻结，不消费）；**在执行任务继续跑完**；投递仍应用（写 buffer、结算、Skipped 判定），但不派发 | Paused |
| `Pause` | Paused/终态 | no-op（记 debug 日志） | 不变 |
| `Resume` | Paused | 全量扫描：所有 Pending 实例重做就绪判定 + `ready_queue` 去重排序，开始派发 | Running |
| `Resume` | Running/终态 | no-op | 不变 |
| `Cancel` | Running/Paused | `run.cancel=true`；Pending/Ready → Cancelled；Running → 置取消标志 + 标 Cancelled（不等待）；**kill 在飞执行（M2 abort / M3 杀 worker 进程组，§3.9.4）**；清队列；flush trace | Cancelled + `RunFinished` |
| `Cancel` | 终态 | no-op | 不变 |
| 暂停中收到新投递 | Paused | 正常应用（写 buffer / Skipped 级联），不派发 | 仍 Paused |
| 暂停中 run 静默 | Paused | **不结束**（静默判定只在 Running 下生效） | 仍 Paused |

**在飞 LLM 的取消**：`Harness` 持有 `CancellationToken`，cancel 时 drop future/中断 HTTP 流；Python 节点/工具运行在 worker 子进程中，取消走 §3.9.4 的 `cancel` 帧 → 信号升级（用户代码在安全点自检 `ctx.cancel_requested`，04 §4.2）。

## 3.9 超时、kill 与看门狗（关闭审计 C-01/C-07/M-18/S-07/S-09）

### 3.9.1 三层预算

| 层 | 默认 | 执行者 | 到期动作 |
|---|---|---|---|
| 实例（节点） | 180s | 事件循环（deadline 表）→ worker supervisor | **杀进程组**；迁移 `TimedOut` → `fail_run`；`killed_workers += 1` |
| 单次 LLM | 60s（重试 1 次） | Harness | `HARNESS_LLM_TIMEOUT` → Crashed |
| 单次工具 | 30s | ToolExecutor（worker 子进程） | `TOOL_ERROR` 喂回 LLM（不终止）；工具超时同样杀进程组 |

> 约束：`node_timeout ≥ llm_timeout × (1 + retries) + 工具预算`，启动时校验配置，违反记 warning。

### 3.9.2 kill 语义（D1，替代 v1.2 的 stop-waiting）

- **超时 = 杀进程组**：实例 deadline 到期后，事件循环把实例迁 `TimedOut` 并立即 `fail_run`；supervisor 对 worker **进程组**（含孙进程）执行升级终止。
- **终止顺序（固定）**：`cancel` 帧 → 宽限 **2s** → `SIGTERM` → 宽限 **1s** → `SIGKILL`（协议见 `schemas/worker-protocol-v1.md` §4）。被 kill 的 worker 数累加 `RunMetrics.killed_workers`。
- **不产生 `NodeAbandoned`**：v2 不存在"任务仍在跑但被放弃"的记账对象；`NodeAbandoned` 事件与 `NODE_ABANDONED` 码标 deprecated，`RunMetrics.abandoned_tasks` **恒 0**（保留字段兼容）。
- **无残留**：终止后 supervisor 必须 `wait`/reap，断言进程组无存活子进程（AC-06）。
- **M2 等价物**：in-process `FakeExecutor` 用 tokio task `abort()` 表达同一语义（到达 TimedOut、停止等待、`killed_workers += 1`），无真实 OS 进程；真进程组 kill 的验收在 M3（ISSUE-047）。
- **迟到结果**：实例已 TimedOut → 丢弃（3.6）。

### 3.9.3 watchdog（Tick 每 1s）

| 检查 | 动作 |
|---|---|
| Running 实例 `now - started_at > timeout` | 迁 TimedOut → kill 进程组 → fail_run（`killed_workers += 1`） |
| 无 Running/Ready、`ready_queue` 空、但仍存在 Pending 实例，且 `now - last_event_at > deadlock_grace_ms` | `RUN_DEADLOCK` → fail_run |
| `killed_workers > 0` | 每 10s 记一次指标（`abandoned_tasks` 恒 0，不再检查） |
| 终态实例出现非终态 buffer（不应发生） | Internal 告警 |

> 关闭审计 C-07：Pending 卡死由"静默 + Pending 存在"检测，不再只看 Running。

### 3.9.4 进程组隔离与 kill（M3 真 worker）

| 步 | 动作 | 失败/边界 |
|---|---|---|
| 1 | supervisor 以**独立进程组** spawn worker（`setsid`/`process_group(0)`），stdin/stdout 走 NDJSON 协议 | spawn 失败 → `NODE_WORKER_CRASH` |
| 2 | 超时/取消：先发 `cancel` 帧，等待宽限 **2s** 让用户代码在安全点退出 | 无响应 → 升级信号 |
| 3 | `SIGTERM` 到**进程组**（`kill(-pgid)`），宽限 **1s** | 仍存活 → `SIGKILL` |
| 4 | `wait`/reap 主进程，断言进程组无残留（孙进程一并终止） | 有残留 = 验收失败（AC-06） |
| 5 | 记录 `killed_workers += 1`；实例 TimedOut/Cancelled；run 按冷峻失败或取消收尾 | 不产生 `NodeAbandoned`；`abandoned_tasks` 恒 0 |

> M2 无 OS 进程，"kill" = `task.abort()`；上表为 M3 起（`crates/zgraph-worker`）的验收口径。SPAWN/协议细节见 `schemas/worker-protocol-v1.md` §2–§4。

## 3.10 终止判定（关闭审计 C-10/S-06）

```text
is_quiescent(run) =
   no instance with status ∈ {Pending, Ready, Running}
   AND ready_queue.is_empty()
   AND no pending deliveries in flight
```

- 静默且 `status == Running` → 聚合 end 输出（01 §1.9）→ `RunFinished{Completed}` → 结束。
- 静默且 `status == Paused` → **不结束**（等 Resume/Cancel）。
- 冷峻失败路径优先于静默判定（fail_run 先置终态）。

## 3.11 事件循环禁则（I8 的可检查清单）

| 禁止 | 替代 |
|---|---|
| `import` / 调任何用户 Python 函数（含 gate、工具、签名检查） | M3：worker 子进程（supervisor 异步等待）；M2：执行任务内（`FakeExecutor`） |
| 同步 SQLite 写 | `trace_tx.send()`（不可丢用 await，流式用 try_send） |
| `std::fs` 大文件读写 | 启动时加载；运行期不读 |
| `Mutex` 阻塞锁 > 1ms | 用通道传递状态 |
| `.await` 在持锁/持引用期间 | 先取快照再 await |

## 3.12 trace 背压与不可丢（双通道）

采用**双通道**（与 00 §0.5 默认值一致；关闭审计 C-24 的可丢/不可丢混排）：

> **M2 临时口径（ISSUE-033，已由 M6 撤销）**：M2 的 `zgraph-trace` 曾用**单通道 `sync_channel(8192)`**——不可丢事件阻塞 `send`、流式事件 `try_send` 失败即丢弃计数；可丢/无损语义等价但容量统一 8192。**M6 已拆回下表双通道（8192 + 1024）且不改公开 `TraceHandle` API（REV-041）**；跨发送端无序口径见 06 §6.4.1（ISSUE-092）。以 06 §6.4.1 为准。

| 通道 | 容量 | 生产者 | 策略 |
|---|---|---|---|
| `trace_tx`（不可丢） | `TRACE_CHANNEL_CAP = 8192` | 事件循环 / worker supervisor | `send().await`；满则背压并记 `trace_backpressure`（实测 10k 条 36ms，正常不会满；M2 内核 sink 同步调用，指标恒 0，见 ISSUE-045） |
| `stream_tx`（可丢） | `STREAMING_CHANNEL_CAP = 1024` | 节点 `ctx.emit` / Harness | `try_send`；满则丢弃 + `streaming_dropped` 计数（汇总进 `RunFinished.metrics`；M6 起为真实双通道，REV-041） |

- 两个通道由 **06 的单一写线程**消费（`select`/合并）：Streaming 在写线程内按 100ms 窗口聚合成"分段"后落库（06 §6.5），**不落逐 token**；不可丢事件走批量事务 256 行/100ms。
- 不可丢清单：`RunStarted` / `Transition` / `GateResult` / `NodeTimedOut` / `NodeAbandoned`（v2 不产生）/ `RunFinished`（00 §0.3）。
- 事件循环只在 **trace_tx** 上可能被背压；`stream_tx` 永不阻塞事件循环（`try_send`）。

## 3.13 多 run 并发

- `RunManager { runs: HashMap<RunId, RunHandle> }`：每个 run 一个事件循环 task + 一个 executor 通道 + 一个 watchdog task。
- 共享只读：`Arc<CompiledGraph>`、`Arc<EdgeIndex>`、全局 worker 名额（`MAX_WORKERS`）、`TraceWriter` 句柄。
- 隔离：`RunState` 不跨 run；`global_vars`/`user_id` 每 run 独立；每 run worker 名额（`MAX_WORKERS_PER_RUN = 8`）独立计数，worker 进程不跨 run 复用（D4/D8）。
- 上限：`max_concurrent_runs`（默认 32），超出 → 启动失败 `RUN_TOO_MANY`（v1 由调用方决定，不做排队）。

## 3.14 优雅退出

1. 停止接受新 run；
2. 对所有 run 发 `Cancel`（→ kill 进程组，§3.9.4）；
3. 等待 ≤ `SHUTDOWN_GRACE_MS`（5s）：事件循环收尾、flush trace；
4. `runtime.shutdown_timeout(5s)` → 若仍超时 `shutdown_background`（尚未退出的 worker 进程组强制 `SIGKILL`，文档写明）；
5. 关闭 SQLite（WAL checkpoint）、打印被 kill 的 worker 计数（`killed_workers`；`abandoned_tasks` 恒 0）。

## 3.15 运行期错误处理矩阵（汇总）

| 错误 | 检测点 | 动作 | run 结果 | trace |
|---|---|---|---|---|
| 非法迁移 | `transition()` | Internal → fail_run | Failed | error |
| 投递到终态实例 | `apply_completed` | RUN_DELIVERY_TO_TERMINAL → fail_run | Failed | error |
| 任务 panic | 执行器 panic 捕获 | NodeError::Internal → Crashed → fail_run | Failed | error |
| 实例超时 | deadline/watchdog | TimedOut → **kill 进程组** → fail_run；`killed_workers += 1` | Failed | error + NodeTimedOut（`NodeAbandoned` 不产生，D1） |
| worker 握手失败 | supervisor | `NODE_WORKER_HANDSHAKE` → Crashed（`NodeWorker{Handshake}`）→ fail_run | Failed | error |
| worker 协议错误 | supervisor | `NODE_WORKER_PROTOCOL` → Crashed（`NodeWorker{Protocol}`）→ fail_run | Failed | error |
| worker 导入/签名失败 | worker 启动 | `NODE_WORKER_IMPORT` → Crashed（`NodeWorker{Import}`）→ fail_run | Failed | error |
| worker 被信号杀死/异常退出 | supervisor | `NODE_WORKER_CRASH` → Crashed（`NodeWorker{Crash, signal, exit_code, stderr_tail}`）→ fail_run；记录 signal/exit + stderr 尾部（≤1 KiB、不脱敏；仅 supervisor 观察到的进程退出路径有三项证据，握手/协议/导入/worker 自报 crash/spawn 失败均省略） | Failed | error |
| 静默 + Pending | watchdog | RUN_DEADLOCK → fail_run | Failed | error |
| gate 异常 | 执行任务 | passed=false（拦截），continue | 不变 | warning + GateResult.error |
| gate 非 bool | 执行任务 | passed=false + 类型错误记录 | 不变 | warning |
| worker Python 初始化失败 | worker spawn/启动 | `NODE_WORKER_IMPORT` / `NODE_WORKER_CRASH`（v2 无进程内解释器初始化；`RUN_PYTHON_INIT` 保留兼容） | Failed | error |
| trace 写失败（磁盘满/IO/DB 损坏） | 写线程 | **fail-stop**：M2 由 `TraceHandle::take_error`/`flush`/`close` 暴露，run 生命周期接线在 M3/M5（ISSUE-036）；接入后通知事件循环取消 run、CLI 退出码 4，不静默降级 | Failed | error |
| 取消 | 控制通道 | 3.8 | Cancelled | info |

> **M5 补充（ISSUE-066，REV-031）**：`NodeError::NodeWorker` 的 `signal`/`exit_code`/`stderr_tail` 是**只增**的崩溃证据字段（错误码与 `Display` 不变）；JSON canonical 形状与边界见 06 §6.2.5.1，公开 variant 增字段的 source-breaking 备注见 08 §8.7。
