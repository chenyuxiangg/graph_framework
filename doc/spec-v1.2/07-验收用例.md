## AC-01 示例图端到端跑通

- **前置**：`--fake-llm`，脚本让 `input_parser` 返回 `{"parsed_query":"退款政策","user_id":"u1"}`、`kb_search` 返回 `{"kb_result":{"hits":1}}`、`answer_writer` 返回 `{"answer":"可以退款","need_human":false}`。
- **步骤**：
  ```bash
  zgraph validate tests/fixtures/graphs/customer_ticket.json
  zgraph run tests/fixtures/graphs/customer_ticket.json \
    --inputs '{"input_parser":{"user_message":"我要退款"}}' \
    --assets-dir tests/fixtures/graphs/customer_ticket \
    --fake-llm=tests/fixtures/graphs/customer_ticket/fake_llm.json \
    --db /tmp/ac01.sqlite --json
  ```
  > **`--fake-llm` 口径（M5，REV-028）**：裸 `--fake-llm` = CLI 内置默认脚本（内容不保证确定），确定性验收必须用 `--fake-llm=<script>`；AC-01 的脚本与完整资产由 REV-032 交付（已合并）；命令形状即 M5 契约。
- **预期**：
  - `validate` 退出码 0，人类可读输出匹配 02 §2.7.4 格式（`✓ graph valid: 6 nodes, 6 edges, 0 subgraphs (graph_hash=…)`）；
  - `run` 退出码 0，JSON 中 `status="Completed"`；`run_output = {"result": <answer_writer 整包 output>}`，`run_output.result.content` 为字符串（需二次解析出 `answer`、`need_human`），`run_output.result.stop_reason` 存在（整包广播语义，04 §4.5 / 05 §5.9.2）；

## AC-03 trace 完整性与回放

- **步骤**：跑 AC-01 后执行 `zgraph trace <run_id> --json > trace.json`。
- **预期**：
  - 事件序列以 `RunStarted` 开头、`RunFinished` 结尾，**恰好各一次**（I5）；
  - 每个实例的迁移链合法（用 01 §1.2.3 矩阵校验）：首迁移 ∈ {`Pending→Ready`, `Pending→Skipped`}（Skipped 实例只有这一条迁移），末迁移为终态；
  - `seq` 单调递增；`zgraph trace` 能按 seq 重建时间线；
  - 不可丢事件数 = 预期数（无缺口）；
  - Streaming 事件可按 instance 聚合为文本，且 `RunFinished.metrics.streaming_dropped` 可读。

## AC-05 冷峻失败：Python 异常

- **前置**：`nodes/boom.py` 抛 `RuntimeError("boom")`；图：`start → boom → end`。
- **预期**：

## AC-06 超时杀进程组不挂死

- **前置**：`nodes/slow.py` 执行 `time.sleep(30)`（可再派生孙进程以验证进程组）；节点 `timeout_ms=1000`。
- **步骤**：`zgraph run ... --json`，计时；用 `pgrep -g <pgid>`/`kill(pid,0)` 检查残留。
- **判定（v2/D1，M3 真 worker 口径）**：
  - **进程组被 kill**：`cancel` 帧 → 2s → `SIGTERM` → 1s → `SIGKILL`（对进程组，含孙进程）；
  - **无残留子进程**：reap 后进程组内无存活 PID（AC 断言）；
  - **run 在 5s 内失败**：不等待 30s；实例 `TimedOut`、run `Failed`（`NODE_TIMEOUT`），退出码非 0；
  - trace 有 `NodeTimedOut`；`killed_workers ≥ 1`；`NodeAbandoned` **不产生**、`abandoned_tasks` **恒 0**；
  - 进程正常退出（`shutdown_timeout` 生效）。
- **M2 口径**：in-process `abort()` 无真实 OS 进程组；仅断言「5s 内 Failed + `TimedOut` + `killed_workers ≥ 1` + `NodeTimedOut` 事件」。真进程组 kill 的验收在 **M3**（ISSUE-047）。

## AC-07 事件循环不阻塞

- **方法（M3 起真 worker）**：测试内注入 5ms ticker（复用 `doc/analysis/spike/src/bin/t2_gil.rs` 方法；spike 源已入库），跑含 **真 worker 子进程**的图（每节点 `time.sleep(0.3)`）。
- **预期**：事件循环 ticker 最大间隔 **< 50ms**；worker 执行期间循环仍能处理控制命令（Pause 在 100ms 内生效）。
- **反例保护**：若在事件循环线程同步 `wait` worker 子进程（而非异步等待），本用例必须失败（v2 无进程内 Python；见 D1/D4）。
- **M2 口径**：用 in-process sleep 节点（`FakeExecutor`）跑同一 ticker 断言；真 worker 场景在 **M3** 补齐（ISSUE-047/054）。

- **断言**（`ac08a_fake_llm_tool_loop_streams_tokens_into_trace`）：
  - `agent_call` 输出四字段 `{content, stop_reason, iterations, usage}`，`content` 为脚本最终文本；run `Completed`、`run.error_code = null`；
  - 流式 1:1 emit：token 段拼接 == 最终 `content`（无丢弃前提下）；`progress` 每轮恰好一条（percent 按 §5.8.2）；`tool_call_start/end` 各至少一次且 `call_id` 一致；

  - 请求 `tools` schema 顺序与 `AgentConfig.tools` 一致（05 §5.6.3）；`usage.total_tokens > 0` 且 = prompt + completion；
  - **失败路径同一文件覆盖**：`tool_exception_is_fed_back_and_run_continues`（工具异常 → `TOOL_ERROR{reason:"exception"}` 喂回、run 继续）、`tool_timeout_is_fed_back_and_run_continues`（`timeout_ms=300` 超时 → 杀进程组 + `TOOL_ERROR{reason:"timeout"}` 喂回、run 继续且 < 15s）、`unknown_tool_crashes_instance`（未注册工具 → `HARNESS_UNKNOWN_TOOL` → Crashed）。

- **步骤**：跑 AC-01 的图（agent 节点真实模型）。
- **硬断言（e2e-dev 实测口径，避免模型行为不可控导致 flaky）**：
  - `agent_call` 节点 `Completed`，`content` 非空且输出含 `{content, stop_reason, iterations, usage}`；
  - `usage.total_tokens > 0`；
  - trace 中 token 聚合非空（`streaming_events` 可拼出非空正文）。
  - **不硬断言** `ToolCallStart/ToolCallEnd`（模型是否调用工具不可控；若调用则按 05 §5.6.6 语义校验）。
- **手动口径说明**：真实模型**不硬断言工具调用**（模型是否调用 `add` 等 fixture 工具不可控，避免手动验收 flaky）；工具链路由 fake 档 a–c 用**真 Python worker 子进程**覆盖（`ac08a`/`tool_exception_*`/`tool_timeout_*`/`unknown_tool_crashes_instance`）。重跑 3 次成功率 ≥ 2/3（容忍模型波动），失败时错误码映射正确；结果记录 trace 证据即可，不进入 `doc/test-baseline.txt`；失败不得用重试掩盖（错误码按 05 §5.7 映射）。

## AC-09 并行分支与确定性

- **图**：`start → {a_py, b_py} → merge → end`（a/b 为 Python sleep 0.2s，merge 需两输入）。
- **预期**：
  - a、b 的 Running 区间重叠（时间差 < 50ms），总耗时显著小于串行（含进程冷启动；**阈值：M3 实测后回填**，初值 < 1.0s 仅为占位，v2 偏差 D8）；
  - `merge` 收到两端口各一份数据；`trigger=all` 就绪语义正确；
  - **确定性**：同输入连续 5 次 run，`transitions` 的节点顺序集合一致（允许并行分支内部交错，但状态与最终输出一致）；
  - 覆盖语义：同一端口两次投递时后者覆盖（v1 单数据源），trace 可见两条投递。
- **口径**：M2 只有 in-process 逻辑并行（无进程冷启动，不用于定阈值）；**M3 起真 worker 子进程**跑本用例并回填阈值（ISSUE-047/054）。

## AC-10 暂停/恢复/取消

- **暂停**：run 含 2 个串行 Python 节点（各 0.3s），第 1 个执行中发 Pause → 第 2 个不派发；等待 1s 无新 Running；Resume 后完成。
- **取消**：执行中发 Cancel → run `Cancelled`、无 `Failed`；在飞实例 `Cancelled`；`RunFinished` 恰一次；后续事件被忽略。
- **幂等**：重复 Pause/Resume/Cancel 不改变结果、不重复 `RunFinished`。

## AC-11 死锁检测

- **图构造**：`a → b`，但 a 的出边 gate 恒 false，且 b 是唯一 end 的前置。
- **预期**：
  - b 被级联 `Skipped`（若其全部入边结算）→ run 正常 `Completed`，**不**误报死锁；
  - 人为制造"入边永不结算"：测试构建启用 `RunOptions.test_hooks.disable_settle=true`（03 §3.2，`feature = "test-hooks"`）→ 静默超过 `deadlock_grace_ms` 后 run `Failed`，`error.code=RUN_DEADLOCK`，不无限挂起。生产构建无该入口。

## AC-12 多 run 并发隔离

- **契约**：并发启动 10 个 run（同图、不同 `run_id`；独立 db 或同 db 不同 run_id）；全部 `Completed`；每个 run 的 `instances/gate_results/events/transitions/streaming_events` 只属于自己；`global_vars`/`user_id` 不串；全局 `MAX_WORKERS` 与每 run `MAX_WORKERS_PER_RUN` 上限生效（v2 偏差 D8/D4；不再使用 CPU=1/IO=4 信号量）。
- **M5 实测组合（REV-029，`tests/e2e/ac12.rs`）**：
  - **8 个纯 python run**：同一张三并发分支图（`start → {a,b,c} → done`，真 worker + 真 SQLite），用于 `user_id`/`global_vars` 隔离与全局/每 run 峰值度量；
  - **2 个含 `agent_call` 的 run**：`start → echo(python) → answer_writer(agent) → end`，fake LLM + 工具 `add` 走真 worker 子进程（复用 `tests/fixtures/graphs/harness_ac08/**`），覆盖「完整栈」并发；
  - **同库形态**：10 个 run 全部写**同一 SQLite**（同 db 不同 `run_id`，AC 允许的更强形态）；独立 db 形态由 M3 `concurrency.rs` 覆盖。
- **M5 实测口径（本机 8 核 / macOS，2026-10-30 连跑 3 次）**：
  - `WorkerExecutor::with_limits(4, 2)`：**全局峰值 4**（= 全局上限）、**每 run 峰值 2**（8 个 python run 均达到且不超过；2 个 agent run 为 1）；真实进程区间共 26 段（8×3 + 2×1）；
  - 单 run 基线 **792–846ms**、10 run 并发总耗时 **2.46–2.54s**、比值 **2.9–3.1**（REV-029 评审独立复跑为 0.84–0.95s / 2.61–2.72s / 2.86–3.10，属机器负载差异；只记录不硬断言绝对值）；
  - **同库 10 并发写未触发 `SQLITE_BUSY`/写端错误（3/3）**：WAL + 5s `busy_timeout` + 写线程 busy 重试；若未来慢盘/大流量出现写端错误，按 AC 措辞退化为「独立 db」组合并登记台账。
- **断言**：全部 `Completed` 且无 `error_code`；逐 run 查询精确计数 + 跨 run `instance_id` 互斥；`global_vars`/`user_id` 回显逐 run 互异；全局峰值断言 `峰值 <= 全局上限 && 峰值 >= 2`（避免低核 CI flake；实测达到 4 不写死 `==4`）；每 run 峰值 `<= per_run` 且观测到 `==2`；总耗时/单 run 比值 `< 10`（仅证伪「完全串行 ≈10x」）。
- **已知边界（ISSUE-079 注记）**：AC-12 的全局/每 run 上限只覆盖 `WorkerExecutor` 的 python 节点子进程；`agent_call` 的工具调用由 Harness 的**独立进程级信号量**（容量 CPU×2）约束，**不占**上述全局/每 run 许可、也不在区间日志内——不得据此认为「全栈所有 worker 子进程都受全局上限」，统一留 M6。
- **与原文的偏差**：原文「10 个 AC-01 run 同图」在 M5 未字面满足（M5 实测 8+2 组合已覆盖更强核心语义）。REV-032 收敛了 REV-029 Nits（补 ISSUE-079 口径边界注释、统一基线数字、说明防御性 `run_id` 断言、`RoutingExecutor` 转发 `timeout_hint`），但**未新增 10×同图用例**；如需该形态留后续/M6。
- **口径**：完整多 run 隔离验收在 **M5**（依赖完整栈）；M2 仅覆盖 run 级内存状态隔离（ISSUE-047/054）。

> **L3 幂等/外部副作用（引用 04 §4.3.7）**：AC-05/AC-06/AC-10/AC-12 的"重跑 / 异常隔离 / 超时 kill / 多 run 隔离"均以用户 worker 的 L3 声明为前提——框架只保证进程隔离与可观测，**不承诺外部副作用可回滚**；L3 本身不在可自动断言的验收项内（ISSUE-022/067）。
