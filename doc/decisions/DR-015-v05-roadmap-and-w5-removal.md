## 1. 背景与 W5 定义

W5「共享评审队列」原定义（DR-004 §3）：**一个评审节点按到达顺序排队处理多份投递**——评完一个放行一个；需要节点邮箱/多次激活/按 item 路由，属内核级改动。

## 2. 不做理由

1. **能力已覆盖**：
   - per-item 评审节点（每个工作 agent 配独立评审节点）满足「每个 item 独立评审」；
   - `foreach` 动态 N 提供**节点内并行**（W4b，v0.2+）；
   - `human_decisions`/`decide` 提供**人工决策队列**（W3a，v0.2+）。
   - 三者组合覆盖共享评审队列的**可观察需求**，无需内核级邮箱。
2. **内核成本高**：W5 需节点邮箱/多激活/按 item 路由，改动调度器（多激活语义、背压、取消、优先级），并影响 trace/replay 确定性（同一节点多次激活/投递顺序）。
3. **回放/兼容风险**：新增多激活状态会扩展状态机/迁移矩阵/trace schema 与 L2 语义，破坏「默认路径逐字节不变」与既有回放承诺；收益与风险不匹配。
4. **需求未验证**：无真实用户/工作流证据表明需要「单评审节点排队」；现有 per-item 节点 + foreach 已在 software_team SOP v1.2 验证。
5. **机会成本**：v0.5 更应投入 `reexec`、真实 Codex/DSH 验证、ISSUE 清理、sandbox Linux/构建工具与可观测性；W5 会挤占这些高价值项。

## 3. 替代方案（未来若出现真实需求）

| 需求形态 | 推荐 |
|---|---|
| 每个 item 独立评审 | 现有 **per-item 评审节点**（无需改动） |
| 节点内并行 fanout | 现有 **`foreach`**（W4b） |
| 人工决策排队 | 现有 **`human_decisions`/`decide`** |
| 限制并发评审数 | 未来可评估**轻量「节点并发上限」**（不引入邮箱/多激活；仅调度层配额，语义/trace 兼容成本低） |
| 邮箱/多激活式共享队列（原 W5） | **不做**；若用户坚持，另立 DR 重新评估（需明确真实工作流与回放方案） |
